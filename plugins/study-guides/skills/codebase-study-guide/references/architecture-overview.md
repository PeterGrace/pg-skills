# Architecture Overview — template

Write to `docs/study-guide/00-architecture-overview.md`. This is the top-down anchor doc.
Keep it skimmable for the mixed audience: an ops reader should get the shape of the system
from the headers and tables alone, while an engineer can follow the lifecycle walk and file
references into the code.

Start with the provenance header, then follow this structure.

```markdown
> Generated by codebase-study-guide on <YYYY-MM-DD> from commit <short-hash>.
> Verify flagged items with a subject-matter expert before relying on this.

# Architecture Overview

## What this system does
<One short paragraph in plain language. What problem does it solve, for whom?
Verifiable from README/docs/code — if you have to guess, say so.>

## The big picture
<A simple diagram of the major subsystems and how they connect. Prefer a Mermaid
`flowchart` or a clean ASCII block diagram. Keep it to the handful of boxes that matter.>

## Subsystems
| Subsystem | Responsibility | Location |
|-----------|----------------|----------|
| <name>    | <one line>     | <path/>  |

## Lifecycle: <name the primary path, e.g. "an HTTP request">
<The centerpiece. Trace ONE real path end to end, step by step, citing the file/symbol at
each hop. This is what turns a list of folders into an understanding of how the system
actually runs. Example shape:>
1. Request enters at `<entrypoint>` (`path/to/file: symbol`).
2. Routed to `<handler>` (`path/...`), which validates …
3. …
4. Response serialized at `<path/...>` and returned.

## Cross-cutting concerns
<Where these live, with file references. Omit any that don't apply.>
- **Configuration:** <where config is loaded/validated>
- **Authentication / authorization:** <where>
- **Logging / observability:** <where>
- **Error handling:** <patterns used, where>
- **Persistence / state:** <datastores, where accessed>

## External dependencies and integrations
<Key third-party services, APIs, queues, databases the system talks to, and where those
boundaries live in code.>

## Build, run, and test
<The actual commands and their source, e.g. from package.json scripts or a Makefile.
Where does someone start the app locally? Run the tests?>

## Open questions / verify with an SME
<Anything you inferred, couldn't trace, or found confusing. Be specific and reference the
file so a reviewer can resolve it quickly.>
```

Guidance:
- The lifecycle walk is the most valuable section — invest there. If there are two or three
  genuinely distinct primary paths (e.g. a web request, a background job, a CLI command),
  trace each briefly rather than blending them.
- For the diagram, only draw boxes you can point to in the code. A small honest diagram
  beats an impressive speculative one.
- Resist describing *why* the architecture is shaped this way unless a doc or comment states
  it. Describe the shape; route the "why" to Open questions.
