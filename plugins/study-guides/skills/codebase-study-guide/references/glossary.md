# Glossary — template

Write to `docs/study-guide/glossary.md`. The glossary is often the highest-leverage doc for
a mixed team: it gives support/ops staff and engineers a shared vocabulary, which is exactly
what lets them talk precisely about the system (and to an LLM about changes to it).

Collect terms as you read: domain/business concepts, internal jargon, acronyms, codenames,
and named code constructs (classes, services, key variables) whose meaning isn't obvious.

```markdown
> Generated by codebase-study-guide on <YYYY-MM-DD> from commit <short-hash>.
> Verify flagged items with a subject-matter expert before relying on this.

# Glossary

<Alphabetical. One entry per term.>

### <Term>
- **Type:** domain term | code construct | acronym | codename
- **Meaning:** <plain-language definition>
- **Appears in:** `<path/...>` <and other notable locations>
- **Notes:** <disambiguation, common confusions, or "meaning inferred — verify">
```

Guidance:
- Define terms in plain language first; an ops reader shouldn't need to read code to
  understand the entry.
- Distinguish a term's **domain** meaning from any **code** construct that shares its name —
  these often drift apart and the gap is a frequent source of miscommunication.
- If a term's meaning is inferred rather than documented, mark it and add it to the
  verification checklist. Domain terms especially are worth an SME's confirmation.
- Don't pad with generic programming vocabulary ("function," "class," "API"). Include a term
  only if a newcomer to *this* system would plausibly be confused by it.
