# Module Deep Dive — template

Write one file per module to `docs/study-guide/modules/<module-name>.md`. Read the module's
key files before writing. The goal: someone could read this and then have an informed
conversation about changing the module, without having read every line themselves.

```markdown
> Generated by codebase-study-guide on <YYYY-MM-DD> from commit <short-hash>.
> Verify flagged items with a subject-matter expert before relying on this.

# Module: <name>

**In one line:** <what this module is responsible for>

**Location:** `<path/to/module/>`

## Responsibilities
<What this module owns, and just as importantly, what it does NOT own (where the boundary
is). 2–5 bullets.>

## Key files
| File | Role |
|------|------|
| `<path>` | <what it contains / does> |

## Public interface
<How the rest of the system uses this module: the functions, classes, endpoints, events, or
CLI commands it exposes. Name them and cite where they're defined. This is the contract —
the part most relevant when discussing changes.>

## How it works
<A grounded walk through the module's main behavior. Cite files/symbols. Describe the data:
what comes in, how it's transformed, what goes out. Keep "what" verifiable; mark any "why"
or inference explicitly.>

## Dependencies
- **Depends on (internal):** <other modules it calls, with paths>
- **Depended on by:** <who calls this module, if known>
- **External:** <libraries / services it uses>

## Gotchas and non-obvious behavior
<The things that would bite someone making a change: implicit ordering, shared mutable
state, surprising defaults, retry/timeout logic, places where the name misleads. Cite the
file for each. If you found none, say "None identified" rather than padding.>

## Open questions / verify with an SME
<Inferences and unknowns specific to this module, each with a file reference.>
```

Guidance:
- "Depended on by" can be expensive to determine precisely; a grep for imports/usages is a
  reasonable basis, but if you're unsure, note the uncertainty rather than asserting.
- The **Gotchas** section is disproportionately useful for a team that will be changing the
  system — prioritize finding the genuine traps over listing obvious facts.
- Keep each deep dive self-contained enough to read alone, but link to the architecture
  overview and related modules by relative path where it helps.
