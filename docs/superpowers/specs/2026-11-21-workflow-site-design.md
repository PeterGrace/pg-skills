# Workflow site design

**Date:** 2026-11-21
**Status:** Approved in brainstorming; awaiting spec review

## Goal

A public documentation site for `PeterGrace/pg-skills` that explains how Peter Grace
starts and executes his agent workflows, so the people who ask can copy them. It is
built with Astro Starlight, organized by Diataxis, and served from GitHub Pages at
`https://petergrace.github.io/pg-skills/`.

## Audience

Both groups, copiers first:

- **Copiers:** engineers who use Claude Code and want to run the same workflows on
  their own repositories. Tutorials, how-to guides and adaptation guidance are
  written for them.
- **Observers:** people who want the approach without installing anything. The
  explanation pages are written for them.

## What the site may name

Real names, no infrastructure. The site names Peter Grace, Brooke
(`brooke-reviews[bot]`), and his projects (okf_mcp, autobots, claims-mcp, the
knowledge catalog) as worked examples. It never contains hostnames, IP addresses,
internal URLs, cluster or registry names, or private repository names. Where an
example needs one, it uses `example.com` or `example.internal`.

## Scope of the first draft

Five areas:

1. Idea to merged PRs: plan, epic and sub-issues, `issue-implementer` subagents,
   Brooke's review, addressing it, merging, close-out.
2. Backlog burndown: grooming, and working through the `accepted` label.
3. Study guides: generate, fact-check, reconcile.
4. Validating that things work with claims-mcp and `claims-audit`.
5. The supporting setup: knowledge catalog, model policy, worktree and machine
   hygiene.

Out of scope: a custom domain, search beyond Starlight's built-in Pagefind,
translations, and diagrams beyond those the explanation pages need.

## Information architecture

**Home:** a short landing page saying what this is and who it's for, with two entry
points: *Try it* (first tutorial) and *How I work* (the lifecycle explanation).

**Tutorials** (learning by doing):

1. Your first issue to merged PR: install the plugins, file a small issue on a
   sandbox repo, run `github-issue-to-pr`, read the review, address it, merge.
2. Your first epic with subagents: plan a two- or three-task milestone, file
   sub-issues, run `github-epic-to-merged-prs`, close out the epic.
3. Your first study guide: generate, fact-check and reconcile a guide for a small
   repo.

**How-to guides** (one goal each):

- Plan a feature into an issue
- Plan a milestone into an epic and sub-issues
- Groom a vague issue
- Split an issue into sub-issues
- Execute an epic with subagents
- Burn down the `accepted` backlog
- Answer review-bot comments
- Close out an epic
- Validate a change with claims-mcp and `claims-audit`
- Fact-check and reconcile a study guide
- Adapt the skills to your setup (reviewer bot, gates, models, Forgejo instead of
  GitHub)

**Reference** (generated from the repository; see below):

- One page per plugin and per skill: description and triggers, plugin, install
  commands, link to the source `SKILL.md`
- The `issue-implementer` agent: its description, model and standing rules
- Glossary, rendered from `GLOSSARY.md`

**Explanation** (the why):

- How I work: the lifecycle end to end, including when I burn down a backlog
  instead of running an epic
- Why I fact-check generated docs: study guides as a write, check, reconcile loop
- Why one subagent per issue, in its own worktree, merging into an integration
  branch
- Why a review bot, and what Brooke checks
- Why audit claims: what gates miss and claims-mcp catches
- The model policy: Sonnet first, and when work escalates to Opus
- The knowledge catalog as long-term memory
- Working on a shared machine: worktrees, caches, gate locks

## Build

### Layout

```
site/
  package.json            exact pinned versions; package-lock.json committed
  astro.config.mjs        site + base, Starlight config, sidebar by folder
  src/content/docs/
    index.mdx             home
    tutorials/
    how-to/
    explanation/
    reference/
      generated/          gitignored; written by the generator on every build
```

`astro.config.mjs` sets `site: "https://petergrace.github.io"` and
`base: "/pg-skills"`. The sidebar has four groups, Tutorials, How-to guides,
Reference and Explanation, each autogenerated from its folder.

### Generated reference

`tools/skills.py` gains a `reference --out <dir>` subcommand. It runs the existing
validation first and refuses to write if validation fails. It then writes:

- `plugins/<plugin>.md`: the plugin's description, version, category, keywords,
  install commands for each client, and a list of its skills linking to their pages;
- `skills/<skill>.md`: the skill's description, its plugin, any Claude Code
  frontmatter keys it sets, and a link to its `SKILL.md` on GitHub (`main` branch);
- `agents/<agent>.md`, for each file in a plugin's `agents/`: its name as Claude
  Code addresses it (`<plugin>:<agent>`), description, model, and the agent body;
- `glossary.md`: the body of `GLOSSARY.md`, with Starlight frontmatter added.

Every page carries Starlight frontmatter (`title`, `description`) and a note that it
is generated and should not be edited. Output is deterministic, so a rebuild with no
source change produces identical files. The subcommand gets unit tests in
`tests/test_skills_tool.py` alongside the existing ones, and passes `mypy --strict`.

### Recipes

- `just site-gen`: runs the generator into `site/src/content/docs/reference/generated`.
- `just site-dev`: `site-gen`, then `npm run dev` in `site/`.
- `just site-build`: `site-gen`, then `npm ci` and `npm run build` in `site/`.

`just check` is unchanged: it doesn't need Node.

### Link checking

The site uses the `starlight-links-validator` plugin, so a broken internal link
fails the build.

## Deployment

A new workflow, `.github/workflows/pages.yml`:

- **Triggers:** pushes to `main` and pull requests touching `site/**`,
  `plugins/**`, `catalog.yaml`, `GLOSSARY.md` or `tools/**`; also
  `workflow_dispatch`.
- **Build job:** checkout, setup-uv, setup-node, install just, `just site-build`,
  then upload the `site/dist` artifact with `actions/upload-pages-artifact`.
- **Deploy job:** on `main` only, runs `actions/deploy-pages` in the
  `github-pages` environment, with `pages: write` and `id-token: write`.

Every action is pinned to a full commit SHA, as `ci.yml` already does.

One-time setup: set the repository's Pages source to "GitHub Actions" with `gh api`.
That is an outward-facing change, so it needs Peter's go-ahead when the time comes.

## Release behaviour

`ci.yml`'s release job currently tags every push to `main` that passes. It changes to
skip tagging when every file changed since the latest `v*` tag is under `site/` or
`docs/`. If there is no tag yet, or any other path changed, it tags as it does today.

## Content process

### Phase 1: skeleton

Scaffold, generated reference, deployment and the release skip. The live site has
the home page and the reference section only. Tutorials, how-to and explanation
pages appear as they are written, never as placeholder pages.

### Phase 2: interview

Structured Q&A, one question at a time and mostly multiple choice. Questions are
built from what the skills already say, so Peter confirms or corrects how he
actually works rather than how the skills describe it. Order:

1. How he starts and chooses a workflow
2. Idea to merged PRs
3. Backlog burndown
4. Validating with claims-mcp
5. Study guides
6. The supporting setup

Answers are recorded in `docs/site-interview.md`, one section per area, so the
source of every page is in the repo.

### Phase 3: writing

- **Voice:** explanation pages, and how-to pages describing his own practice, are in
  Peter's first person ("I start by…"). Tutorials, and the steps of how-to pages,
  address the reader ("you").
- **One Diataxis type per page:** tutorials teach a beginner through a guaranteed
  outcome; how-tos give steps for one goal and assume competence; explanations give
  reasons and trade-offs and contain no steps; reference states facts.
- **Review:** each area is published once Peter has reviewed it.

### Phase 4: checking

- `just site-build` passes, including the link validator.
- Each tutorial step is checked against the current `SKILL.md` text.
- A fresh subagent, on a different model from the writer, runs `claims-audit` on the
  pages' factual claims about the skills, checked against the skill files.
  Refuted claims are fixed before an area is published.

## Success criteria

- `https://petergrace.github.io/pg-skills/` serves the site, and a push to `main`
  that changes a skill updates its reference page without a hand edit.
- A docs-only push doesn't create a release.
- The reader of the first tutorial ends up with a merged PR on a sandbox repo.
- Every one of the five areas has at least one how-to page and is covered by at
  least one explanation page, each reviewed by Peter.
- No page contains a hostname, IP address or private repository name.
